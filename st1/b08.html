2. 학습 시작 멘트

혼자 만든 좋은 함수가 아니라, 함께 연결되는 좋은 프로그램 만들기

7차시에서 우리는 해결할 문제를 정하고, 사용자와 입력·출력, 핵심 기능과 역할을 계획했습니다. 오늘은 그 계획을 실제 코드로 바꾸는 날입니다. 그런데 팀 프로젝트에서는 한 사람이 모든 기능을 만드는 것이 아닙니다. 누군가는 데이터를 읽고, 누군가는 분석하고, 다른 누군가는 결과를 화면에 보여 줄 수 있습니다.

각 팀원이 맡은 기능을 잘 만들었다고 해도 서로 연결되지 않으면 하나의 프로그램이 되지 않습니다. 데이터 모듈은 리스트를 반환했는데 분석 모듈은 문자열을 기대하거나, 같은 이름의 함수가 여러 파일에 존재하거나, 라이브러리 설치 환경이 다르면 통합 과정에서 문제가 생깁니다.

또한 이미 만들어진 좋은 기능을 활용하는 것도 중요한 개발 능력입니다. 우리는 라이브러리와 오픈소스를 올바르게 선택하고, 기능을 모듈로 나누고, 공통 인터페이스를 정해 역할별 코드를 연결합니다. 오늘의 목표는 코드의 양이 아니라 함께 작동하는 시제품을 만드는 것입니다.

4. 개념 및 상세 설명 · 관련 코드 · 코드별 확인 문제

개념 1. 라이브러리 활용: 필요한 기능을 다시 만들지 않고 연결하기

프로젝트를 구현할 때 모든 기능을 처음부터 직접 만들 필요는 없다. 라이브러리(library)는 자주 사용하는 기능을 미리 구현해 둔 코드의 모음으로, 필요한 기능을 불러와 재사용할 수 있게 한다.

파이썬과 함께 제공되는 표준 라이브러리에는 math, random, statistics, datetime 등이 있고, 별도로 설치하여 사용하는 외부 라이브러리에는 데이터 처리·시각화·인공지능 등 다양한 기능이 포함될 수 있다.

중요한 것은 단순히 라이브러리를 많이 사용하는 것이 아니라, 프로젝트 목표에 필요한 기능인지, 입력과 출력 형태가 맞는지, 설치와 실행 환경에서 사용할 수 있는지를 판단하는 것이다.

표준 라이브러리외부 라이브러리기능 재사용
import math import statistics values = [4, 9, 16, 25] roots = [] for x in values: roots.append(math.sqrt(x)) mean_value = statistics.mean(roots) print("제곱근:", roots) print("평균:", mean_value)

코드 1 확인 문제: 옳은 것을 모두 고르시오. (3개)

정답: ①, ②, ③
라이브러리는 검증된 기능을 재사용하도록 도와준다. 다만 함수의 입력·출력, 설치 여부, 실행 환경과 프로젝트 목적을 함께 확인해야 한다.
개념 2. 오픈소스 활용: 공개 코드에도 사용 규칙이 있다

오픈소스(open source)는 소스 코드가 공개되어 누구나 살펴볼 수 있고, 정해진 라이선스 조건에 따라 사용·수정·배포할 수 있는 소프트웨어이다.

오픈소스라는 이유만으로 저작권이 사라지는 것은 아니다. 프로젝트에서 오픈소스 코드나 라이브러리를 활용할 때는 프로젝트 이름, 사용 목적, 공식 출처, 라이선스, 수정 여부를 기록하는 것이 좋다.

이 기록은 단순한 형식이 아니라, 다른 팀원이 어떤 코드를 왜 사용했는지 이해하고 이후 수정·배포 과정에서 라이선스 조건을 지키는 데 필요한 협업 정보이다.

라이선스출처저작권활용 기록
library_log = { "name": "example-library", "purpose": "데이터 처리", "source": "공식 저장소", "license": "사용 조건 확인", "modified": False } for key, value in library_log.items(): print(key, ":", value)

코드 2 확인 문제: 옳은 것을 모두 고르시오. (3개)

정답: ①, ②, ③
오픈소스는 공개된 코드이지만 라이선스와 저작권 조건이 존재할 수 있다. 출처와 활용 목적, 수정 여부까지 기록하면 프로젝트의 투명성이 높아진다.
개념 3. 모듈화: 하나의 큰 프로그램을 역할이 분명한 기능으로 나누기

7차시에서 프로젝트의 기능을 입력·처리·저장·분석·출력으로 나누었다면, 8차시에서는 그 구조를 실제 코드로 옮긴다. 이를 모듈화(modularization)라고 한다.

모듈화는 프로그램을 의미 있는 기능 단위로 나누는 과정이다. 각 함수는 가능한 한 하나의 분명한 역할을 맡고, 함수 이름·매개변수·반환값을 통해 다른 기능과 연결된다.

이 구조를 사용하면 한 팀원이 데이터 입력 기능을 수정해도 분석 기능 전체를 다시 작성할 필요가 없으며, 기능별 테스트와 디버깅도 쉬워진다.

기능 분리함수 역할재사용개별 테스트
def load_data(): return [18, 21, 19, 23] def analyze_data(data): return sum(data) / len(data) def make_message(average): return f"평균 온도: {average:.1f}℃" data = load_data() average = analyze_data(data) message = make_message(average) print(message)

코드 3 확인 문제: 옳은 것을 모두 고르시오. (3개)

정답: ①, ②, ③
기능을 함수별로 분리하면 역할과 데이터 흐름이 명확해진다. 이는 협업, 테스트, 수정과 재사용을 쉽게 한다.
개념 4. 인터페이스 설계: 팀원이 만든 모듈을 연결하는 공통 약속

여러 팀원이 서로 다른 기능을 구현하면 코드 내부 구조가 달라도 최종 프로그램에서는 연결되어야 한다. 이때 필요한 것이 인터페이스(interface)이다.

인터페이스는 함수 이름, 매개변수의 의미와 자료형, 반환값의 의미와 자료형처럼 모듈 사이에서 주고받는 정보의 규칙이다.

예를 들어 데이터 수집 모듈은 점수 목록을 list로 반환하고, 분석 모듈은 그 리스트를 입력으로 받기로 미리 정하면 서로 다른 사람이 작성해도 쉽게 통합할 수 있다.

매개변수반환값자료형공통 규칙
def get_scores(): return [82, 91, 76, 88] def calc_average(scores): return sum(scores) / len(scores) scores = get_scores() average = calc_average(scores) print("입력 자료형:", type(scores)) print("결과:", average)

코드 4 확인 문제: 옳은 것을 모두 고르시오. (3개)

정답: ①, ②, ③
인터페이스는 모듈 간의 연결 규칙이다. 함수 이름, 매개변수, 반환값, 자료형과 의미가 일치해야 안정적으로 통합할 수 있다.
개념 5. 협업 코드 통합: 기능별 코드를 하나의 데이터 흐름으로 연결하기

협업 구현에서는 팀원이 맡은 기능을 따로 작성한 뒤 공통 인터페이스에 맞추어 하나의 프로그램으로 통합한다.

통합할 때는 단순히 코드를 한 파일에 붙이는 것이 아니라, 함수 이름 충돌, 전역 변수 의존, 자료형 불일치, 호출 순서, 반환값 누락처럼 기능 연결 과정에서 발생할 수 있는 문제를 점검해야 한다.

가장 좋은 방법은 입력 → 처리 → 결과 생성 → 출력의 흐름을 먼저 만들고, 각 단계가 예상한 값을 다음 단계로 전달하는지 단계별로 확인하는 것이다.

통합데이터 흐름자료형 일치실행 순서
def input_module(): return [3, 7, 5, 9] def analysis_module(data): return max(data), min(data) def output_module(result): high, low = result return f"최댓값={high}, 최솟값={low}" data = input_module() result = analysis_module(data) message = output_module(result) print(message)

코드 5 확인 문제: 옳은 것을 모두 고르시오. (3개)

정답: ①, ②, ③
협업 코드는 데이터 흐름을 기준으로 연결한다. 각 모듈의 반환값과 다음 모듈의 입력 형식이 일치하는지 확인하는 것이 중요하다.
개념 6. 핵심 기능 시제품과 개발 일지: 구현 과정을 남기며 개선하기

시제품(prototype)은 최종 프로그램을 완성하기 전에 핵심 기능이 실제로 동작하는지 확인하기 위한 초기 구현이다. 8차시에서는 모든 기능을 완벽하게 구현하기보다 가장 중요한 입력 → 처리 → 출력 흐름을 먼저 연결한다.

동시에 개발 일지에는 오늘 구현한 기능, 사용한 라이브러리, 발생한 문제, 원인, 해결 방법, 다음 작업을 기록한다. 이 기록은 팀원이 서로 진행 상황을 공유하고, 다음 차시의 테스트·디버깅 과정에서 문제를 재현하는 데 활용된다.

좋은 개발 일지는 단순히 “코드를 작성함”이라고 쓰는 것이 아니라, 무엇을 구현했고 어떤 문제가 있었으며 어떻게 해결했는지가 드러나야 한다.
