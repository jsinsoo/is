2. 학습 시작 멘트

“실행된다”에서 “믿고 사용할 수 있다”로

8차시에서 우리는 여러 기능을 연결하여 핵심 기능 시제품을 만들었습니다. 프로그램이 화면에 결과를 출력했다면 구현의 중요한 단계는 통과한 것입니다. 하지만 한 번 실행되었다는 사실만으로 프로그램이 완성되었다고 말할 수는 없습니다.

입력이 0일 때는 어떻게 될까요? 허용 범위의 가장 끝값에서는요? 사용자가 문자를 입력하거나 빈 데이터를 전달하면 어떻게 될까요? 결과가 정확하더라도 지나치게 느리거나, 오류 메시지가 이해하기 어렵거나, 불필요한 개인정보가 노출된다면 좋은 프로그램이라고 할 수 있을까요?

오늘은 시제품을 의도적으로 흔들어 봅니다. 정상·경계·예외 입력으로 테스트하고, 오류를 재현하여 원인을 찾고, 수정 후 다시 검증합니다. 그리고 기능뿐 아니라 개인정보·편향·저작권·라이선스까지 살펴 “작동하는 프로그램”을 “검증되고 개선된 프로그램”으로 발전시킵니다.

4. 개념 및 상세 설명 · 관련 코드 · 코드별 확인 문제

개념 1. 테스트 사례 설계: 정상 입력·경계값·예외 입력을 구분하기

프로그램이 한 번 실행되었다고 해서 올바른 프로그램이라고 판단할 수는 없다. 테스트(test)는 미리 준비한 입력을 프로그램에 넣고 실제 결과가 예상 결과와 일치하는지 확인하는 과정이다.

정상 입력은 일반적으로 기대하는 범위의 값, 경계값은 조건이 바뀌는 최소·최대 또는 바로 주변의 값, 예외 입력은 잘못된 자료형이나 허용 범위를 벗어난 값처럼 프로그램이 특별히 처리해야 하는 입력이다.

좋은 테스트는 “잘 되는 예”만 확인하지 않는다. 실패하기 쉬운 경계와 예외를 의도적으로 포함해야 숨겨진 오류를 발견할 가능성이 높아진다.

정상 입력경계값예외 입력예상 결과
def classify_score(score): if score < 0 or score > 100: return "입력 오류" if score >= 60: return "통과" return "보충" tests = [ ("normal", 80), ("boundary", 60), ("boundary", 59), ("exception", -1) ] for kind, value in tests: print(kind, value, classify_score(value))

개념 2. 테스트 명세: 입력·예상 결과·실제 결과를 기록하기

테스트를 체계적으로 수행하려면 입력값만 나열하는 것보다 테스트 목적, 입력, 예상 결과, 실제 결과, 통과 여부를 함께 기록하는 것이 좋다.

예상 결과는 프로그램을 실행하기 전에 정해야 한다. 실행 후 나온 값을 보고 예상 결과를 바꾸면 프로그램의 정확성을 객관적으로 판단하기 어렵다.

테스트 결과를 표나 리스트로 남기면 어떤 입력에서 실패했는지 다시 확인할 수 있고, 수정 후 같은 사례를 다시 실행하는 재검증에도 활용할 수 있다.

테스트 명세예상 결과실제 결과통과 여부
def double(x): return x * 2 test_cases = [ {"input": 3, "expected": 6}, {"input": 0, "expected": 0}, {"input": -2, "expected": -4} ] for case in test_cases: actual = double(case["input"]) passed = actual == case["expected"] print(case["input"], case["expected"], actual, passed)

테스트 명세는 예상 결과와 실제 결과를 분리하여 기록하고 비교함으로써 프로그램의 정확성을 객관적으로 확인하게 한다.
개념 3. 디버깅 절차: 오류 재현 → 원인 분석 → 수정 → 재검증

디버깅(debugging)은 단순히 오류가 난 줄을 고치는 작업이 아니다. 먼저 같은 입력으로 오류를 다시 발생시키는 재현이 필요하고, 변수 값·조건식·함수 호출·자료형 등을 추적하여 원인을 찾아야 한다.

원인을 찾은 뒤에는 필요한 부분만 수정하고, 오류가 발생했던 테스트를 다시 실행하여 해결되었는지 확인한다. 또한 수정으로 인해 다른 기능이 새롭게 잘못되지 않았는지도 살펴본다.

따라서 좋은 디버깅 기록은 증상 → 재현 입력 → 원인 → 수정 내용 → 재검증 결과의 흐름을 포함한다.

오류 재현원인 분석수정재검증
def average(values): if len(values) == 0: return None return sum(values) / len(values) tests = [ [10, 20, 30], [], [5] ] for data in tests: result = average(data) print("입력:", data, "결과:", result)

정답: ①, ②, ③
디버깅은 오류를 재현하고 원인을 근거 있게 분석한 뒤 최소한으로 수정하고 동일·관련 테스트로 다시 검증하는 과정이다.
개념 4. 기능적 평가: 정확성·효율성·사용성을 함께 살펴보기

프로젝트 산출물은 단순히 “실행되는가?”만으로 평가하기 어렵다. 정확성은 요구한 결과를 올바르게 만드는지, 효율성은 시간과 메모리 등 자원을 지나치게 낭비하지 않는지, 사용성은 사용자가 입력·출력과 오류 메시지를 쉽게 이해할 수 있는지를 살펴보는 관점이다.

예를 들어 결과는 정확하지만 데이터가 조금만 커져도 지나치게 느려진다면 효율성 개선이 필요하다. 오류가 발생했을 때 사용자가 무엇을 잘못했는지 알 수 없다면 사용성 측면의 개선이 필요하다.

기능적 평가는 하나의 기준만 보는 것이 아니라 프로젝트 목표와 사용자 요구를 기준으로 여러 관점을 함께 검토한다.

정확성효율성사용성요구사항
def evaluate(actual, expected, elapsed, message): accuracy = actual == expected efficiency = elapsed < 1.0 usability = len(message) > 0 return { "accuracy": accuracy, "efficiency": efficiency, "usability": usability } result = evaluate( 20, 20, 0.15, "처리가 완료되었습니다." ) print(result)

정답: ①, ②, ③
기능적 평가는 정확성뿐 아니라 효율성과 사용성 등 프로젝트가 실제 목적에 맞게 작동하는지를 여러 관점에서 확인한다.
개념 5. 윤리적 평가: 개인정보·편향을 점검하기

정보과학 프로젝트는 기능적으로 잘 작동하더라도 사용자의 권리나 사회적 영향을 고려하지 않으면 좋은 산출물이라고 보기 어렵다. 개인정보는 목적에 필요한 최소한만 수집하고, 불필요한 식별 정보가 저장·출력되지 않는지 확인해야 한다.

편향(bias)은 특정 집단이나 조건의 데이터가 지나치게 많거나 적어 결과가 한쪽으로 치우치는 문제와 관련될 수 있다. 따라서 데이터 구성과 결과가 특정 사용자에게 지속적으로 불리하게 작동하지 않는지 점검한다.

윤리적 평가는 프로그램 개발이 끝난 뒤 형식적으로 추가하는 절차가 아니라, 문제 정의·데이터 수집·구현·테스트·개선 전 과정에서 반복해서 확인해야 하는 기준이다.

개인정보 최소화편향공정성사용자 권리
records = [ {"name": "학생A", "score": 90}, {"name": "학생B", "score": 80} ] safe_records = [] for r in records: safe_records.append({ "score": r["score"] }) print(safe_records)

정답: ①, ②, ③
윤리적 평가는 필요한 정보만 다루고 데이터와 결과의 편향 가능성을 점검하여 사용자의 권리와 공정성을 고려하는 과정이다.
개념 6. 저작권·라이선스 점검과 개선본 만들기

8차시에서 활용한 오픈소스와 라이브러리는 9차시 평가에서도 다시 확인해야 한다. 사용한 코드·이미지·데이터·라이브러리의 출처와 라이선스가 기록되어 있는지, 수정·배포 조건을 지켰는지 점검한다.

평가에서 발견한 문제는 단순히 표시하는 데서 끝나지 않는다. 우선순위를 정하여 수정하고, 다시 테스트하여 실제로 개선되었는지 확인해야 한다. 이 과정을 통해 초기 시제품 → 테스트 보고서 → 평가표 → 개선본이 연결된다.

최종적으로는 “무엇을 바꾸었는가?”뿐 아니라 왜 바꾸었고, 어떤 근거로 개선되었다고 판단했는가를 설명할 수 있어야 한다.

저작권라이선스개선 우선순위재검증
review = { "accuracy": "통과", "privacy": "개선 필요", "license": "출처 확인", "action": "개인정보 제거", "retest": "통과" } for item, result in review.items(): print(item, ":", result)

5. 학습 마무리 멘트

좋은 프로그램은 오류가 없는 프로그램이 아니라, 검증하고 개선할 수 있는 프로그램이다

오늘 우리는 프로그램을 단순히 실행해 보는 것과 체계적으로 테스트하는 것이 다르다는 점을 확인했습니다. 정상 입력만으로는 발견하기 어려운 문제를 경계값과 예외 입력을 통해 찾았고, 오류를 재현하고 원인을 분석하여 수정한 뒤 다시 검증했습니다.

또한 프로그램의 품질은 정답을 출력하는 것만으로 결정되지 않습니다. 같은 결과를 더 효율적으로 만들 수 있는지, 사용자가 쉽게 이해할 수 있는지, 개인정보를 불필요하게 다루지는 않는지, 데이터와 결과가 편향되지는 않는지, 외부 자료의 저작권과 라이선스를 지키고 있는지도 함께 살펴야 합니다.

오늘 작성한 테스트 보고서·기능 및 윤리 평가표·개선본은 프로젝트가 어떤 근거로 좋아졌는지를 보여 주는 기록입니다. 다음 10차시에서는 문제 발견부터 설계·구현·테스트·개선까지의 프로젝트 전체 흐름과 Ⅲ단원 알고리즘을 연결하여 2차고사 전 범위를 종합적으로 정리합니다.
